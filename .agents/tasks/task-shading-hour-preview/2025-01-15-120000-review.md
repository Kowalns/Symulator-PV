# Single-hour shading preview endpoint and panel grid visualization

Adds a `POST /api/shading/single-hour` endpoint that computes solar position, per-panel shading, and hourly production (with/without shadow) for a user-selected date and hour. The frontend gets a new section in `report.html` with a date/hour picker and a CSS-grid visualization that color-codes each panel by shading degree. The backend orchestrates existing service functions (`oblicz_zacienienie_pojedyncza_godzina`, `oblicz_poa_tmy`, `oblicz_wydajnosc_panela`) and stitches the results into a single response. Watch for: TMY index overflow for leap-year dates silently zeroes production (confirmed); the `_dzien_roku` helper is imported as a private function coupling the handler to solar_position internals (confirmed).

**Verdict**: APPROVED

## High-level view

TMY data is indexed as `(day_of_year - 1) * 24 + hour`, which maps cleanly to a non-leap-year 8760-element array. For leap-year dates past Feb 28, day_of_year can reach 366, pushing the index beyond the array. The bounds check gracefully falls back to zero irradiance, so the server doesn't crash, but the user gets an incorrect "zero production" result for any leap-year date after February. More subtly, dates in March–November of a leap year fetch the wrong hour (shifted by 24 positions) even though the index stays in bounds.

The handler imports the private helper `_dzien_roku` from `solar_position`. This is stable but couples the handler to another module's internals — `datetime.date(...).timetuple().tm_yday` is a stdlib one-liner that removes the coupling.

The test suite covers input validation thoroughly (10 cases), the night path, and the daytime path with mocked TMY data. No test exercises the leap-year index shift.

1. **Leap-year TMY index overflow** — For any date after Feb 28 in a leap year, `_dzien_roku` returns up to 366, making the TMY index exceed 8759 or point to the wrong hour (off-by-24 for March–November). The bounds check silently falls back to zero irradiance for the overflow case, producing incorrect zero-production results. Fix: use `tmy_index = (min(dzien_roku, 365) - 1) * 24 + godzina` or `tmy_index % 8760`.
2. **Private function import (`_dzien_roku`)** — The handler imports a leading-underscore helper from `solar_position`. If the module restructures its internals, the handler breaks at import time. Replace with `datetime.date(rok, miesiac, dzien).timetuple().tm_yday` or promote the helper to a public function.

## TMY indexing and the leap-year boundary

The core of the production computation relies on looking up the correct hour in the 8760-element TMY arrays:

```python
dzien_roku = _dzien_roku(rok, miesiac, dzien)
tmy_index = (dzien_roku - 1) * 24 + godzina
```

PVGIS TMY data always contains exactly 8760 entries (a "typical" non-leap year). When a user picks a leap-year date — say 2024-03-01 — `_dzien_roku` returns 61 instead of 60, shifting every subsequent hour by 24. For December 31 in a leap year, the index hits 8783, which exceeds the array length. The handler's defensive check:

```python
if dane_tmy and tmy_index < len(dane_tmy.get("ghi", [])):
```

catches the overflow and falls back to `ghi=0, dni=0, dhi=0`. This prevents a crash, but the user sees "production: 0 Wh" for a sunny afternoon — a silent data error rather than a clear failure. For dates earlier in a leap year (March through November), the off-by-one doesn't overflow but fetches data from the wrong hour (shifted by 24 positions). The fix is `tmy_index = (min(dzien_roku, 365) - 1) * 24 + godzina` or equivalently `tmy_index % 8760`.

## Private-API coupling

The import `from backend.services.solar_position import _dzien_roku` reaches into the module's internal namespace. Either drop the underscore (making it a public utility) or replace with `datetime.date(rok, miesiac, dzien).timetuple().tm_yday` from stdlib, which is one line and has no import coupling.
