# Single-plane layout and real RCE prices from PSE API

Two changes ship together: the installation layout is simplified from a multi-row grid (rows × columns) to a single plane (one row of N panels side by side), and the RCE pricing module is upgraded from a static synthetic 12×24 table to real 15-minute data fetched from the PSE public API (`api.raporty.pse.pl/api/rce-pln`), cached locally as 783 days of hourly averages. The tariff model is corrected — G11f was previously treated as a flat-price tariff (`cena_calkowita_zl_kwh`), now it's correctly dynamic: RCE hourly price + seller markup + G11f distribution fees.

Watch for: SSL certificate verification is disabled for the PSE API client, meaning the cache-update path is vulnerable to MITM (confirmed); the `liczba_kolumn` field survives as dead weight in `InstallationConfig`, always set equal to `liczba_paneli`, creating a divergence trap if any future caller forgets to synchronize them (confirmed); the day-by-day fetching strategy (`pobierz_dane_rce_z_pse`) makes one HTTP request per day — 783 sequential requests with no rate limiting or retry logic — which is fragile for the initial cache population (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The layout simplification removes `odstep_miedzy_rzedami_cm`, `liczba_rzedow`, and the multi-row loop. The `liczba_kolumn` field remains in the dataclass but is always set to `liczba_paneli` — dead code that creates a divergence trap.

The G11f tariff correction is the high-value change: it previously returned a static `1.0091 zł/kWh`, now it computes `RCE(month, hour) + 0.04 narzut + 0.2180 dystrybucja + fees` — correctly modeling the hourly variation that makes G11f attractive for PV owners with dynamic pricing. The fallback to synthetic data when cache is missing ensures the system degrades gracefully.

The PSE client disables SSL verification (`CERT_NONE`) and fetches day-by-day without retries or backoff. For a cache populated once and committed to the repository this is operationally bounded, but the code is structured to allow runtime cache updates via `aktualizuj_cache_rce()`, which means the security and reliability gaps are latent rather than theoretical.

<summary>Issues (4)</summary>

1. **SSL verification disabled for PSE API** — `_utworz_ssl_context()` sets `check_hostname = False` and `verify_mode = CERT_NONE`. If the PSE endpoint has certificate issues, pin or bundle the CA cert rather than disabling verification entirely. At minimum, add a comment explaining why this is needed and document the risk. (confirmed)
2. **Vestigial `liczba_kolumn` field** — `InstallationConfig.liczba_kolumn` is always set to `liczba_paneli` by every caller. It's never read independently of `liczba_paneli` in any production path. Remove it to prevent future divergence. (confirmed)
3. **No retry or rate-limit handling in PSE fetcher** — `pobierz_dane_rce_z_pse` issues one request per day in a tight loop (783+ iterations). Any transient failure silently skips that day (`except Exception: pass`). A network blip mid-run produces a cache with random gaps. Add at least a simple retry (1-2 attempts with backoff) and log skipped days. (confirmed)
4. **Bare `except Exception: pass` hides fetch failures** — In `pobierz_dane_rce_z_pse`, the blanket exception suppression means HTTP 429 (rate limit), DNS failures, and malformed responses are all silently swallowed. At minimum, accumulate skipped dates and return them alongside the data so the caller can decide whether the cache is usable. (confirmed)

## SSL verification disabled

```python
def _utworz_ssl_context() -> ssl.SSLContext:
    ctx = ssl.create_default_context()
    ctx.check_hostname = False
    ctx.verify_mode = ssl.CERT_NONE
    return ctx
```

The comment says "Wymagane przez API PSE" but PSE's API serves a valid Let's Encrypt certificate — this is likely a workaround for a certificate chain issue on the build machine. Disabling verification means any MITM between the server and `api.raporty.pse.pl` can inject arbitrary price data into the cache. Since this cache directly drives economic calculations (prosumer savings, battery ROI), tampered prices could mislead investment decisions.

## Sequential day-by-day fetching

```python
while dzien <= koniec:
    try:
        rekordy = _pobierz_dzien_z_pse(data_str, ctx)
        ...
    except Exception:
        pass  # Silently skip failed days
    dzien += timedelta(days=1)
```

For 783 days, this makes 783 sequential HTTPS requests with no backoff. The PSE API supports OData `$filter` with range queries (`business_date ge '...' and business_date le '...'`), which would reduce this to a handful of paginated requests. The bare `except Exception: pass` means the caller has no visibility into whether 50 days were silently dropped — the resulting cache could have arbitrary gaps without any signal.

## Vestigial `liczba_kolumn`

The field exists in `InstallationConfig` with default `10`, but every construction site sets it to `liczba_paneli`:

```python
# handlers.py (both call sites)
liczba_kolumn=liczba_paneli,

# installation_layout.py (output dict)
"liczba_kolumn": config.liczba_paneli,  # not even reading config.liczba_kolumn
```

If a future caller constructs `InstallationConfig(panel_id=..., liczba_paneli=20)` without explicitly setting `liczba_kolumn`, the default `10` diverges from `liczba_paneli=20`. Nothing reads `liczba_kolumn` in any computation, so the divergence is silent — but it leaks into the serialized output dict, potentially confusing frontend consumers.
