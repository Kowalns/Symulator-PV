# Shadow animation page with solar position endpoint (v2)

This change adds Step 4 ("Wizualizacja cienia") to the PV Simulator: a new page with a Three.js 3D bird's-eye shadow view and a per-panel efficiency heatmap, driven by a new `GET /api/solar-position` endpoint. The animation loop polls both `/api/solar-position` and `/api/shading/single-hour` at 15-minute time steps, using `setTimeout` chaining to prevent request pileup and caching shading responses per hour. An error indicator surfaces after 2+ consecutive fetch failures.

Watch for: The `consecutiveFetchErrors` counter is shared between two independent fetch functions, so a single success in one resets the counter even while the other endpoint is persistently failing (likely). The day-of-month validation gap (Feb 30 accepted) remains from v1 — low severity since the `<input type="date">` enforces valid dates client-side, but the API contract is inconsistent (confirmed).

**Verdict**: APPROVED

## High-level view

The three blocking issues from v1 are resolved. `setInterval` is replaced by `setTimeout` chaining that awaits `updateFrame` before scheduling the next tick, eliminating frame pileup at high playback speeds. Shading data is cached by `date|hour` key so the expensive POST to `/api/shading/single-hour` fires once per hour boundary rather than every 15-minute step. Both fetch functions now track consecutive errors and render a fixed-position red banner when the count hits 2, hiding it on the next successful response.

The shared error counter introduces a quirk: within `updateFrame`, the solar fetch runs first and resets the counter on success *before* the shading fetch fires. When only the shading endpoint is down, the indicator will flicker every frame as solar clears what shading just set.

The `/api/solar-position` handler validates `dzien` ∈ [1, 31] independently of month, so February 30 passes validation and produces subtly wrong astronomical results. The frontend date picker prevents this, limiting exposure to direct API consumers.

## Shared error counter behavior

Both `fetchSolarPosition` and `fetchShadingData` increment and reset the same `consecutiveFetchErrors` variable:

```javascript
// In fetchSolarPosition, on success:
consecutiveFetchErrors = 0;
hideErrorIndicator();

// In fetchShadingData, on success:
consecutiveFetchErrors = 0;
hideErrorIndicator();
```

Within a single `updateFrame` call, the sequence is: fetch solar position → (if success, reset counter) → fetch shading data. If the solar endpoint returns 200, the counter resets to 0 before the shading fetch even fires. This means the shading endpoint would need to fail for `MAX_ERRORS_BEFORE_INDICATOR` *consecutive frames* without the solar endpoint ever succeeding in between — which won't happen because solar is fetched first every frame. Net effect: when only the shading endpoint is down, the indicator appears after 2 frames, then solar succeeds on the next frame and clears it, then shading fails again — the banner flickers every frame. Splitting into `solarErrors` and `shadingErrors` would make the indicator stable per endpoint.

## Animation timing after fix

The `scheduleNextFrame` function chains via `setTimeout`:

```javascript
function scheduleNextFrame() {
    if (!isPlaying) return;
    const intervalMs = 1000 / speedMultiplier;
    animInterval = setTimeout(async () => {
        if (!isPlaying) return;
        currentStep++;
        if (currentStep > 64) currentStep = 0;
        document.getElementById('anim-slider').value = currentStep;
        await updateFrame(currentStep);
        scheduleNextFrame();
    }, intervalMs);
}
```

The delay is measured from the *start* of the timeout, not from the end of `updateFrame`, so effective frame rate at 10x will be max(100ms, fetchDuration). Since the shading fetch is cached for 3 out of 4 steps within an hour, only 1 in 4 frames incurs the full round-trip; the other 3 pay only the solar-position latency.
