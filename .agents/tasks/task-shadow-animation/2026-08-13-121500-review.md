# Shadow animation page with solar position endpoint

This change adds Step 4 ("Wizualizacja cienia") to the PV Simulator: a new page with a Three.js 3D bird's-eye shadow view alongside a per-panel efficiency heatmap, driven by a new `GET /api/solar-position` endpoint. The new endpoint is a thin wrapper around the existing `get_solar_position` service; the frontend orchestrates animation by polling both `/api/solar-position` and the existing `/api/shading/single-hour` endpoint at each 15-minute time step, and the 3D view uses Three.js shadow mapping with a `DirectionalLight` positioned by astronomical azimuth/elevation.

Watch for: The animation fires two sequential HTTP requests per 15-minute step without debouncing or cancellation, which at 10x speed (100ms intervals) will queue requests faster than they resolve and cause visual desync (confirmed). The shading endpoint only receives whole-hour granularity while the solar position endpoint receives minute-level precision, creating a mismatch in the panel diagram during sub-hour steps (confirmed). Silently swallowed fetch errors hide backend failures from the user (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The frontend is a single 578-line HTML file with inline CSS, a Three.js scene, and animation logic. It reads parcel/building/installation configs from `localStorage` and drives a time-step animation that fetches sun position + shading data from the backend. The animation timing model has a race condition: at high playback speeds, new interval ticks fire before prior fetches complete, and the only guard (`fetchInProgress` flag) silently drops frames rather than cancelling or queueing — meanwhile the slider and time display advance unconditionally, causing displayed time to diverge from the rendered scene state.

The `/api/shading/single-hour` endpoint is called with only the integer hour — the `minuta` component from the slider is not forwarded — so the panel efficiency diagram shows the same data for all four 15-minute slots within a given hour while the 3D shadow moves every 15 minutes.

Both fetch functions swallow all errors (`catch (e) { /* ignore */ }`) and return `null`, leaving the user with no feedback when the backend is unreachable or returns validation errors during animation.

<summary>Issues (4)</summary>

1. **Request pileup at high speed** — At 10x (100ms interval), two sequential awaits per frame will exceed the interval, causing the time display to desync from the rendered scene. Add request cancellation (AbortController) or use `setTimeout` chaining so the next tick only fires after the current frame resolves.
2. **Shading granularity mismatch** — `fetchShadingData` sends only the integer `godzina` to `/api/shading/single-hour`, ignoring the 15-minute `minuta` offset. The panel diagram stalls for 4 consecutive frames then jumps. Forward the minute or interpolate.
3. **Silent fetch error swallowing** — Both fetch functions catch all errors and return `null` with no user feedback. A persistent backend error leaves the user staring at "---" indefinitely. Show an error indicator when fetches fail for multiple consecutive frames.
4. **No integration test for frontend-backend contract** — The 13 new unit tests cover the handler but nothing verifies the frontend correctly constructs the query params or that the shading payload matches the expected schema.

## Request pileup and frame-drop model

The animation loop uses `setInterval` with the `currentStep++` increment happening unconditionally in the interval callback, while `updateFrame` is async and guarded by a `fetchInProgress` flag:

```javascript
animInterval = setInterval(() => {
    currentStep++;
    if (currentStep > 64) currentStep = 0;
    document.getElementById('anim-slider').value = currentStep;
    updateFrame(currentStep);  // silently dropped if fetchInProgress
}, intervalMs);
```

At 10x speed (100ms), two serial network round-trips at 50-100ms each mean roughly half the frames are dropped. The time display will read "14:30" while the 3D scene still shows the "13:45" sun position because the increment runs outside the guard. Moving the increment inside `updateFrame` after the fetch completes, or switching to `setTimeout` chaining, would eliminate the desync.

## Shading data uses hour-only granularity

`fetchShadingData(dateStr, godzina)` forwards only the full hour to `/api/shading/single-hour`, which itself only accepts an integer `godzina` field (0-23). The panel efficiency diagram updates once per hour while the 3D shadow (driven by minute-level solar position) moves every 15 minutes. The visual effect is four sun-shadow movements between each diagram update. Fixing this requires either extending the backend endpoint to accept a `minuta` parameter or interpolating shading data client-side.

## Silent error handling

```javascript
try {
    const resp = await fetch(`/api/solar-position?${params}`);
    if (resp.ok) return await resp.json();
} catch (e) { /* ignore */ }
return null;
```

If the backend returns a 400 (invalid date) or the server is unreachable, the page shows "---" and leaves the 3D scene in its last-known state. During animation, a 500 on the shading endpoint causes the panel diagram to freeze at its last valid state while the 3D sun keeps moving — a confusing split-brain visual.

## Solar position endpoint — validation gap on day-of-month

The handler validates `dzien` is between 1 and 31 but doesn't cross-check against the actual month (February 30 passes validation). The underlying astronomical algorithm won't crash on invalid dates but will produce subtly wrong output. The frontend's `<input type="date">` enforces valid dates, so exploitation requires a direct API call — low severity but a contract inconsistency. Confidence: confirmed.

## Test coverage gaps

Not tested: the frontend's query-param construction, the interaction between the animation loop and the backend under latency, and whether the shading endpoint responds correctly when called with the payload structure the frontend sends (no integration test).
