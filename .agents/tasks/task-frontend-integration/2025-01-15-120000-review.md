# Step-navigation flow connecting frontend pages to backend API

The change transforms isolated frontend pages into a connected multi-step wizard. A landing page (index.html) displays 3 step cards that track completion via localStorage. The 3D viewer (viewer.html) gains a "save and proceed" button that runs shading simulation and stores results. The energy profile page (energy-profile.html) gets step navigation, corrected tariff names, and a save-and-proceed button. The report page (report.html) auto-loads data from localStorage and triggers report generation on arrival. On the backend, the installation model is simplified to a single-plane layout (removing row/column grid) and tariff identifiers are renamed from `G11f`/`dynamiczna` to `G11f_dynamiczna`/`G11_dynamiczna`.

Watch for: Hardcoded building dimensions in the shading call bypass actual STL model geometry (confirmed). Hardcoded location (`52.23, 21.01` — Warsaw) in the same call ignores any user-specified coordinates (confirmed). No validation prevents navigation to step 3 with partial data, producing a report with default values that could be mistaken for real results (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The wizard flow persists state between pages exclusively through localStorage. Step 1 serializes panel configuration and shading simulation results, Step 2 serializes the energy consumption profile and tariff choice, and Step 3 reads both to pre-fill its input form and auto-generate the report. The frontend is entirely responsible for data consistency across steps — no server-side session.

The shading simulation call in viewer.html fires with hardcoded building geometry (`szerokosc: 10, glebokosc: 8, wysokosc: 8, x: 0, z: -10`) and hardcoded Warsaw coordinates regardless of what STL model was loaded or what parcel dimensions were drawn. The 3D viewer already has scene information from loaded models, but none of it flows into the shading API call.

<details>
<summary>Issues (5)</summary>

1. **Hardcoded building dimensions in shading call** — The viewer.html "save and proceed" button calls `/api/shading/simulate` with `budynek: {x:0, z:-10, szerokosc:10, glebokosc:8, wysokosc:8}` regardless of loaded STL model. Extract actual geometry from the Three.js scene's bounding box, or at minimum expose building dimension fields in the form.
2. **Hardcoded location in shading call** — Same call uses `lokalizacja: {szerokosc_geo: 52.23, dlugosc_geo: 21.01}` (Warsaw). If the user is simulating for a different city, shading and sun-path calculations will be wrong. Propagate coordinates from a form or localStorage.
3. **No guard against step 3 with missing step 1** — `report.html` shows a `missing-data-info` div when both production and consumption are absent, but if only shading data is missing (step 1 skipped, step 2 completed), the report auto-generates with default production values (180-720 kWh/month). These defaults could be mistaken for actual simulation results.
4. **Step 2 completion detection depends on explicit save** — The step-status check on index.html looks for `profil_zuzycia_dane` to mark step 2 complete, but this key is only written by `zapiszIPrzejdz()`, not by `obliczProfil()`. If a user computes a profile but navigates away without clicking save, step 2 appears incomplete while partial data (`zuzycie_miesieczne_kwh`) already exists in localStorage.
5. **`var` scoping in loops** — `report.html` uses `var i` in multiple sequential for-loops within the same function scope. Not a current bug, but fragile against future refactoring into closures or async callbacks.

## Shading simulation with hardcoded geometry

The "save and proceed" button in `viewer.html` constructs the shading payload with a fixed building configuration:

```javascript
budynek: {
    x: 0,
    z: -10,
    szerokosc: 10,
    glebokosc: 8,
    wysokosc: 8
},
lokalizacja: {
    szerokosc_geo: 52.23,
    dlugosc_geo: 21.01
}
```

The viewer loads STL models and has scene-level bounding box information available from `viewer3d.js`. The loaded model's bounding box could be translated into these parameters. Loading a small shed or a large warehouse produces identical shading results. The 3D viewer gives the user the impression that their specific building matters, but it doesn't affect the simulation.

The location hardcoding has the same effect on a different axis: sun path angles (critical for shading) vary significantly between e.g. Szczecin (53.4N) and Rzeszow (50.0N), but the shading result will always reflect Warsaw's latitude.

## localStorage data flow

The cross-page state relies on these localStorage keys:

- `instalacja_config` — written by viewer.html, read by report.html (tilt angle, power)
- `shading_result` — written by viewer.html, read by report.html (monthly production, shading loss %)
- `zuzycie_miesieczne_kwh` — written by energy-profile.html `obliczProfil()`, read by report.html
- `profil_zuzycia_dane` — written only by `zapiszIPrzejdz()`, checked by index.html for step 2 status
- `taryfa` — written by energy-profile.html save, read by report.html

Report.html reads shading loss as `shading.podsumowanie.strata_zacienienie_procent`. The backend shading response nests this field under `podsumowanie.strata_zacienienie_procent`. The frontend stores the full `podsumowanie` object, so the path should resolve. If it doesn't (e.g. a typo in either side), the scenario comparison silently falls back to an 8% hardcoded default without any user-visible warning.

## Step navigation without enforcement

Nothing prevents a user from navigating directly to `pages/report.html` without completing steps 1 and 2. The report page pre-fills with default values (180-720 kWh/month production, 320-520 kWh/month consumption) and auto-generates if at least partial data exists. A user who completed only step 2 would see a report mixing real consumption data with generic production estimates — functionally misleading without any indication that production numbers are placeholders.
