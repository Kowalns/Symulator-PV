# Building position fallback hardening and dark-theme conversion for energy-profile

This change fixes a building-position bug in the 3D viewer where the shading simulation could receive `x=0, z=0` when `parcel_vertices` was absent from `localStorage`, and converts the energy-profile page from its light theme to the Solar Pro dark scheme already used by `report.html`. The viewer fix replaces a fragile single-`isNaN` check with a multi-layer fallback that rejects both `NaN` and zero, falling through to hardcoded `-16.2`/`13.5` defaults. The energy-profile conversion is purely cosmetic — swapping light backgrounds, blue accents, and white tables for dark-surface + amber-accent styling — paired with corrected user defaults (250W base, G11f_dynamiczna selected, 16kWh battery enabled, sell hour 23). Watch for: the zero-rejection logic in `viewer.html` blocks legitimate `x=0` or `z=0` positions (confirmed); console.log statements left in production code (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The viewer's position-fallback strategy has been tightened from "use `||` and a single fallback element" to a three-tier chain: read hidden input → try fallback input → hardcode default. The trigger condition now includes `v === 0`, which means a user who legitimately places a building at coordinate zero will be silently overridden to the default. This is the only behavioral concern in the viewer fix.

The energy-profile page receives a complete CSS overhaul — no structural HTML changes beyond class additions for the step-bar and a few default-value tweaks. The style scope is local (`<style>` block), so it won't bleed into other pages. The defaults now match the user's configuration: 250W base, CO 3000kWh, CWU 1000kWh, G11f_dynamiczna tariff, 16kWh battery checked and visible, sell hour 23.

`przeliczFallback()` — the function called on page load when no parcel vertices exist — now writes hardcoded defaults instead of potentially writing empty strings from empty fallback inputs. This closes the gap where the hidden inputs could end up blank before the user interacts with the form.

## Zero-as-invalid in building position logic

The core fix introduces `v === 0` as an invalidity condition alongside `isNaN(v)`:

```js
x: (function() { var v = parseFloat(document.getElementById('bud-x').value); return (isNaN(v) || v === 0) ? -16.2 : v; })(),
```

The same pattern appears in the simulation payload builder:

```js
if (isNaN(budX) || budX === 0) { ... budX = -16.2; }
```

The coordinate system is relative to the panel array origin, so `x=0` is geometrically valid — it means the building is directly aligned with the panel reference point on the X axis. If the parcel geometry ever produces a computed position that rounds to zero, the user gets silently relocated to the default (confirmed — the code path is unconditional). The safer approach is to check whether the input `.value` was the empty string before parsing, distinguishing "never set" from "set to zero".

The asymmetry extends into `przeliczFallback`: the function correctly accepts a user-typed `0` from the fallback input (passing the `!== ''` check), but that value is then overridden by the `=== 0` guard in the save handler. A user who enters zero gets the default with no feedback.

## Console.log statements left in simulation handler

The diff adds a new `console.log`:

```js
console.log('[SYMULACJA] FINAL budX=' + budX + ' budZ=' + budZ + ' (should be -16.2/13.5 if no parcel)');
```

Three other console.log statements were already present (pre-existing, but the new one is in-scope). Together they expose coordinate payloads in DevTools — not a security risk, but a code-quality issue for production (confirmed — four statements total at lines ~502-505).
