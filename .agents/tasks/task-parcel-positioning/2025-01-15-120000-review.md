# Parcel boundary positioning via line intersection

A new service computes building and panel center positions from user-specified distances to the southern and eastern parcel boundaries. The algorithm identifies the two relevant edges of an irregular polygon, constructs parallel lines offset by the given distances (plus half-object-dimension), and intersects them to find the object center. A reverse function recovers distances from an arbitrary position. Two POST endpoints expose this math, and the frontend wires distance inputs to the 3D scene with bidirectional sync (distance change moves the object; dragging the object updates distance fields).

Watch for: rotation matrix mismatch between backend and frontend corner calculation (confirmed); hardcoded panel dimensions in frontend diverge from any single source of truth (confirmed); the `typ_obiektu` parameter is accepted but never used in computation (confirmed).

**Verdict**: APPROVED

## High-level view

The roundtrip tests prove numerical consistency to sub-millimeter precision. The boundary selection heuristic silently picks a "wrong" boundary if the parcel shape doesn't have clear E-W and N-S edges — for the known hardcoded parcel this works, but the API accepts arbitrary vertices with no error signal when the heuristic fails.

The frontend corner-distance display uses a rotation matrix that disagrees with the backend's convention. The computed NE-SW distance will be wrong for any azimuth other than 0 or 180. This is purely informational (doesn't affect positioning), but it shows a value the user may rely on for panel spacing decisions.

The bidirectional sync uses a boolean flag (`__aktualizacjaOdleglosciWToku`) to prevent feedback loops. The flag is set *after* the fetch resolves, not before, so two rapid drag events can both enter `aktualizujOdleglosci` before either sets the flag — producing duplicate API calls and a potential flicker in the distance fields.

The API handlers duplicate 80+ lines of identical validation boilerplate between `handle_parcel_position` and `handle_parcel_distance`, creating a maintenance liability when the vertex format or error messages need updating.

## Rotation convention conflict in corner distance display

The backend computes corners with:
```python
gx = cx + lx * cos_a + lz * sin_a
gz = cz + lx * (-sin_a) + lz * cos_a
```

The frontend computes the NE corner with:
```javascript
var neX = budX + neLocalX * cosA - neLocalZ * sinA;
var neZ = budZ + neLocalX * sinA + neLocalZ * cosA;
```

For NE = `(+halfW, -halfD)` and azimuth 350 (10 degrees off north):
- Backend: `neX = cx + halfW*cos(350) - halfD*sin(350)` → `cx + halfW*0.985 + halfD*0.174`
- Frontend: `neX = cx + halfW*cos(350) + halfD*sin(350)` → `cx + halfW*0.985 - halfD*0.174`

The sign on the `halfD*sin` term is flipped. With `halfD = 9.9m` and `sin(350) = -0.174`, the X-coordinate error is roughly `2 * 9.9 * 0.174 ≈ 3.4m`. The SW panel corner has the same issue. The displayed distance between corners will be off by several meters.

## Boundary identification heuristic

The algorithm selects the southern boundary as the longest edge within 30 degrees of E-W bearing, and the eastern boundary as the longest edge within 30 degrees of N-S bearing with the highest average X. The heuristic has a quiet fallback: if no edges are within 30 degrees of E-W, it picks the two edges closest to E-W bearing regardless of deviation. A diamond-shaped parcel (all edges at 45 degrees) would still produce a result with semantically meaningless "south" and "east" labels and no error signal to the caller.

## Dead `typ_obiektu` parameter

The docstring states "Dla budynku: odleglosc mierzona od SCIANY" and "Dla paneli: odleglosc mierzona od KRAWEDZI" — implying different measurement semantics. The function body treats both identically: it always adds the half-dimension projection regardless of type. The handler validates that the value is `"budynek"` or `"panele"` and rejects anything else, making this misleading API surface that will confuse future callers expecting differentiated behavior.

## Frontend hardcoded panel dimensions

Panel dimensions appear as magic numbers in two locations within the positioning script:
- `panSzer = 5.5; panGleb = 4.0;` in `przeliczPozycje()`
- Same values in `obliczOdlegloscNaroznikow()`

Building dimensions are read from form inputs (`bud-szerokosc`, `bud-glebokosc`), but panels have no corresponding form fields. The reverse call (`aktualizujOdleglosci`) for panels also uses these hardcoded values, so dragging panels and then reading back distances will disagree with what the backend would compute for different dimensions.

## Negative distance on drag past boundary

`oblicz_odleglosc_od_granic` computes signed distances: `odl_srodek - polwymiar`. If the user drags the object past the boundary line, `odl_srodek` becomes negative, producing a negative wall distance. The frontend writes this directly into the input fields (e.g., `-2.3`), and on the next `przeliczPozycje` call, the handler rejects it with "Odleglosci nie moga byc ujemne" (the handler validates `>= 0`). This creates an inconsistent state: the distance field shows a negative number that, if the user triggers recalculation, produces an error — the object stays at its dragged position but the distance fields become unusable until manually corrected.
